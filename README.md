# Мониторинг аренды → Telegram

Раз в 10 минут проверяет новые объявления об аренде квартир на трёх сайтах,
отсеивает неподходящие и присылает остальное в Telegram альбомом фотографий
со ссылкой на объявление.

Ничего, кроме GitHub, поднимать не нужно: расписание — GitHub Actions,
состояние — файл `state.json` в этом же репозитории.

## Источники

| Сайт | Как берём данные | Сортировка по свежести |
|---|---|---|
| **4zida.rs** | список из `ld+json` на странице поиска, детали — из открытого JSON API `api.4zida.rs/v6/ads/<id>` | `?sortiranje=najnoviji` |
| **nekretnine.rs** | всё лежит в `__NEXT_DATA__` на странице поиска, отдельный запрос не нужен | `?criterio=data&ordine=desc` |
| | ⚠️ работает только при локальном запуске, см. ниже | |
| **oglasi.rs** | микроразметка schema.org плюс подписанные поля в HTML | `?s=d` |

Общее для всех: сортируем по свежести, берём первые 1–2 страницы, сверяем ID
с тем, что уже показывали. Полная карточка запрашивается только для новых
объявлений (и только на 4zida — остальные отдают всё сразу), поэтому обычный
проход стоит 5–6 запросов на все три сайта.

### Фотографии

В сообщение уходит альбом из нескольких снимков — сколько именно, задаёт
`photos_per_message` в конфиге (Telegram принимает от 2 до 10).

Откуда они берутся, зависит от сайта. 4zida отдаёт все фото в той же карточке,
которую мы и так запрашиваем. nekretnine кладёт их прямо в выдачу. А oglasi
показывает в списке только одну картинку, поэтому для него добавлен `enrich`:
он открывает страницу объявления и забирает остальные. Это один лишний запрос,
и только для новых объявлений.

Шаблон сообщения один и тот же при любом числе фотографий. Ссылки «Открыть
объявление» и «На карте» идут последней строкой прямо в тексте, а не кнопками:
к альбому Telegram кнопки прицепить не даёт, и ради единообразия их не осталось
нигде. Подпись берётся у первого снимка, лимит 1024 символа — реальные
сообщения укладываются в 600.

### halooglasi.com — не подключён

Весь домен закрыт Cloudflare-челленджем: любой запрос без браузера получает
403 «Just a moment...», включая `sitemap.xml`, который они сами указывают
в `robots.txt`. Чтобы его обойти, нужен headless-браузер, который будет решать
антибот-проверку — это уже обход защиты, а не чтение открытых данных, и такой
код ломался бы после каждого обновления Cloudflare. Их `robots.txt` вдобавок
отдельно запрещает краулеры ИИ-сервисов и ставит `ai-train=no`.

Если сайт нужен — практичнее подписаться на их собственные email-уведомления
о новых объявлениях и настроить пересылку в Telegram.

### nekretnine.rs не работает из GitHub Actions

Сайт использует DataDome и **блокирует IP дата-центров**: с раннера GitHub
любой запрос возвращает 403, с домашнего адреса тот же URL отдаёт 200.
Раннеры вдобавок делят адреса между тысячами пользователей, так что репутация
этих IP выжжена задолго до нас.

Обходить это не будем — резать облачный трафик осознанное решение сайта, а не
техническая случайность. Поэтому у поиска стоит `optional: true`: на CI он
падает тихо, без красной аннотации, а при локальном запуске `watch.py` работает
как обычно и присылает свои объявления.

Цена вопроса, по замеру на живой выдаче: без nekretnine остаётся 7 уникальных
квартир из 9. Одно его объявление дублировалось на 4zida, два были уникальны.

Флаг `optional` можно поставить любому поиску — это значит «если не ответил,
тревогу не поднимаем». Обычные поиски при падении печатают `::error::`
и подсвечиваются на странице запуска.

### Почему это законно и вежливо

- **robots.txt.** На 4zida открыт весь поиск (закрыты избранное, печать,
  `/agenti/`), там же лежит `llms.txt` с прямым приглашением забирать актуальные
  страницы. На nekretnine.rs запрещён внутренний API `/search-list` — поэтому мы
  его и не трогаем, а читаем обычную страницу поиска. На oglasi.rs запрещены
  `/oglasi?q=` и `/oglasi?o=` — наши адреса не из этого раздела.
- **Частота.** Один запрос в секунду, 5–6 запросов раз в 10 минут. Это меньше,
  чем человек, обновляющий вкладку.
- **User-Agent.** Браузерный (иначе nekretnine.rs отвечает 403), но с припиской
  `rent-watcher/1.0`, чтобы в логах сайта было видно, кто ходит и зачем.

## Три особенности, на которые ушло больше всего времени

**ID объявления на 4zida — это MongoDB ObjectId.** В первых 4 байтах лежит
unix-время создания, поэтому точный возраст объявления считается из самого ID,
без единого запроса.

**nekretnine.rs отвечает `103 Early Hints`.** Модуль `http.client` в Python
возвращает этот промежуточный ответ вместо финального `200`, и тело приходит
пустым — на этом молча ломаются и `requests`, и `urllib`. Поэтому в проекте
`httpx`: он разбирает такие ответы правильно.

**nekretnine.rs блокирует по своей же cookie.** Сайт использует DataDome: первым
ответом ставит куку `datadome`, и если вернуть её следующим запросом — 403.
Поэтому куки между запросами не сохраняются. Ровно так по умолчанию ведёт себя
`curl`, из-за чего он работал там, где падал клиент с общим cookie-jar.

## Где хранится состояние

В `state.json` — список ID уже показанных объявлений (с префиксом источника,
чтобы ID разных сайтов не пересекались) и отметка, какие поиски уже проходили
первый запуск. Помним последние 5000 ID, это около 165 КБ.

**Как это переживает GitHub Actions.** Раннер одноразовый: между запусками
не сохраняется ничего, кроме содержимого репозитория. Поэтому цикл замкнут
через git:

1. `actions/checkout` выкачивает `state.json` таким, каким его оставил
   предыдущий запуск;
2. `watch.py` дописывает в него разобранные объявления;
3. шаг «Сохранить состояние» коммитит и пушит — **но только если файл
   изменился**.

Пустые проходы (а их большинство) не создают ни коммита, ни шума. Коммит
появляется ровно тогда, когда нашлась квартира, так что `git log` заодно
становится историей находок.

Зацикливания нет: workflow подписан только на `schedule` и `workflow_dispatch`,
и GitHub принципиально не запускает workflow от коммитов, сделанных через
`GITHUB_TOKEN`.

Альтернативой был `actions/cache`, но он молча промахивается: при промахе
скрипт решил бы, что это первый запуск, тихо проглотил бы все объявления
и ничего не прислал — без единой ошибки в логах. Состояние в git видно глазами.

## Установка

### 1. Telegram-бот

1. Открой в Telegram [@BotFather](https://t.me/BotFather), отправь `/newbot`.
2. Придумай имя и username (должен заканчиваться на `bot`).
3. BotFather пришлёт токен вида `123456789:AAH...` — это `TELEGRAM_BOT_TOKEN`.
4. Напиши своему новому боту любое сообщение (иначе он не сможет тебе ответить).
5. Узнай свой `chat_id` — открой в браузере, подставив токен:
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates`
   В ответе найди `"chat":{"id":123456789` — это `TELEGRAM_CHAT_ID`.

Чтобы уведомления шли вам обоим, создай группу, добавь туда бота и возьми
`chat_id` группы из того же `getUpdates` (у групп он отрицательный).

Важная деталь про группы: у ботов по умолчанию включён Privacy Mode, поэтому
обычных сообщений в группе бот не видит и `getUpdates` вернёт пустой список.
Отправку это не ограничивает — режим стоит оставить включённым. Чтобы всё-таки
получить `chat_id`, напиши в группе команду, адресованную боту: `/start@ИмяБота`.
Такие сообщения он получает и в Privacy Mode.

### Отдельная тема вместо General

Если группа переведена в режим форума (с темами), по умолчанию сообщения
уходят в General. Чтобы писать в конкретную тему, задай `TELEGRAM_TOPIC_ID`.
Узнать его можно двумя способами:

- отправить `/start@ИмяБота` **внутри нужной темы** и найти в `getUpdates`
  поле `message_thread_id`;
- скопировать ссылку на тему (долгое нажатие по ней в списке тем → Copy Link):
  в `https://t.me/c/<группа>/<тема>` последнее число и есть ID.

Переменная необязательная: пустая или отсутствующая — сообщения идут в General.

### 2. Локальная проверка

Один раз — окружение и переменные:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

```bash
cp .env.example .env    # и заполнить значения
```

`.env` подхватывается автоматически — подгружать его в окружение вручную
не нужно. Уже заданные переменные окружения имеют приоритет, поэтому в GitHub
Actions работают секреты, а файла `.env` там нет вовсе.

Дальше четыре режима, от безопасного к боевому:

```bash
.venv/bin/python watch.py --test --dry-run
```

Главная команда для проверки. Берёт по одному подходящему объявлению
с каждого сайта и печатает **готовое сообщение целиком** — ровно то, что ушло бы
в Telegram. Ничего не отправляет и не записывает — токен для этого режима даже не нужен.
Этим же проверяется, что сайты не поменяли вёрстку: если разбор сломался,
будет видно сразу.

```bash
.venv/bin/python watch.py --test
```

То же самое, но сообщения уходят в Telegram. Проверка связи, темы и оформления.

```bash
.venv/bin/python watch.py --dry-run
```

Честная симуляция обычного прохода: сколько объявлений получено с каждого сайта,
сколько прошло фильтры, что было бы отправлено. `state.json` не меняет.
Учти: если состояния ещё нет, каждый поиск отработает как первый запуск —
молча, без сообщений. Чтобы увидеть содержимое, используй `--test --dry-run`.

```bash
.venv/bin/python watch.py
```

Боевой проход: шлёт уведомления и записывает `state.json`.

### Разбор накопившегося

Обычный проход смотрит только верх свежей ленты — две страницы, 40 самых новых
объявлений. Всё, что висело на сайте до того, как ты запустил монитор, он не
увидит никогда: выдача отсортирована по дате создания, и объявление недельной
давности лежит в ней сотни позиций вглубь.

Для первого знакомства с рынком есть отдельный режим:

```bash
.venv/bin/python watch.py --catchup 20 --dry-run
```

Пролистает по 20 страниц на каждый поиск и выведет **всё подходящее, что ещё
не показывали**, с ценами и ссылками. Ничего не отправляет и не записывает,
лимит сообщений в этом режиме не действует — список нужен целиком.

Убери `--dry-run`, чтобы то же самое ушло в Telegram. Там лимит
`max_notifications_per_run` работает, так что за раз придёт не больше 15,
а остальные — при следующем запуске. Виденными помечаются только разобранные,
так что ничего не потеряется.

### 3. GitHub Actions

Залей репозиторий на GitHub, затем Settings → Secrets and variables → Actions →
New repository secret, и добавь секреты: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`
и, если нужна отдельная тема, `TELEGRAM_TOPIC_ID`.

Первый запуск можно сделать руками: вкладка Actions → 4zida watcher → Run workflow.

### Расписание задаётся снаружи

Триггер `schedule` у GitHub — best-effort, и на практике он почти не работает.
Замер на этом репозитории: при `*/10` интервалы между запусками составили
94 и 287 минут, причём отменённых запусков не было — срабатывания просто
не выполняются. Для аренды это бесполезно, хорошие варианты разбирают быстрее.

Зато `workflow_dispatch` запускается мгновенно. Поэтому расписание вынесено
на внешний сервис [cron-job.org](https://cron-job.org), который каждые
10 минут дёргает GitHub API:

```
POST https://api.github.com/repos/<владелец>/<репозиторий>/actions/workflows/watch.yml/dispatches

Accept: application/vnd.github+json
Authorization: Bearer <токен>
X-GitHub-Api-Version: 2022-11-28

{"ref": "main"}
```

Токен — fine-grained personal access token с доступом только к этому
репозиторию и единственным правом **Actions: Read and write**. Фонового
доступа к коду он не даёт. Не забудь про срок действия: когда истечёт,
запуски молча прекратятся.

Cron в самом workflow оставлен подстраховкой на случай, если внешний триггер
отвалится, и выставлен раз в час — чаще GitHub всё равно не выполнит.

**Важно про первый проход.** Каждый поиск при первом запуске молча запоминает
текущую выдачу и не шлёт ни одного сообщения — иначе прилетело бы полсотни
уведомлений о квартирах, которые висят на сайтах неделю. Уведомления начнутся
со второго прохода.

## Настройка фильтров

Всё в [`config.yaml`](config.yaml). Блок `filters` наверху действует на все
поиски; любой поиск может переопределить отдельные поля своим блоком `filters`.

| Поле | Что делает |
|---|---|
| `price_min` / `price_max` | цена в EUR за месяц |
| `m2_min` / `m2_max` | площадь |
| `rooms_min` / `rooms_max` | комнаты; `1.5` = jednoiposoban, `2.0` = dvosoban |
| `furnished` | `yes` / `no` / `null`; **есть только у 4zida и oglasi** |
| `only_private` | `true` — скрыть агентства |
| `exclude_keywords` | отсев по словам в описании и заголовке |

Про `only_private` стоит знать две вещи. На oglasi.rs продавец в выдаче не
показан вообще — такие объявления фильтр пропускает (лучше лишнее сообщение,
чем потерянная квартира), и в сообщении строка про продавца просто не выводится.
А на nekretnine.rs объявлений от частников практически нет — включив этот фильтр,
вы отключите сайт целиком.

### География: осторожно с окрестностями

Заречные районы Нови-Сада — Петроварадин, Сремска-Каменица, Мишелук,
Алибеговац — сайты трактуют по-разному. **4zida и nekretnine включают их
в поиск по Нови-Саду** (проверено по слагам в выдаче: `petrovaradin-…-novi-sad`,
`miseluk-petrovaradin-…-novi-sad`). А **oglasi.rs считает их отдельными
местами**: в хлебных крошках Петроварадина нет Нови-Сада вообще, путь идёт
сразу от «Izdavanje stanova». Поэтому для oglasi заведены три поиска вместо
одного — иначе половина заречья просто не видна.

Мораль: добавляя новый район, не полагайся на то, что он «логически внутри»
города. Проверь по выдаче, что его объявления действительно приходят.

`url` в каждом поиске — адрес со страницы сайта. Накликай фильтры в их
интерфейсе и скопируй адрес из строки браузера: так работают любые фильтры
сайта, включая те, которых нет в конфиге. Сортировку дописывать не нужно.

## Эксплуатация

- **Интервал.** Меньше 5 минут GitHub Actions не даёт, и запуск может
  задержаться на несколько минут под нагрузкой. Для аренды это приемлемо:
  в Нови-Саде публикуется порядка 37 объявлений об аренде в сутки, из них
  под фильтры вроде «700–1000 €, от 60 m²» попадает 4–6.
- **Частота коммитов.** Из 144 запусков в сутки коммит делают те самые 4–6,
  остальные выходят с «коммитить нечего».
- **Минуты Actions.** Для публичного репозитория они бесплатны и не ограничены.
  Если сделать репозиторий приватным — бесплатный лимит 2000 минут в месяц,
  каждый запуск округляется вверх до минуты, а 144 запуска в сутки это
  4320 минут. Квота кончится за две недели: тогда увеличивай интервал в cron.
- **Падение одного сайта не ломает остальные** — ошибка логируется, проход
  продолжается. Если сайт поменяет вёрстку, это будет видно в логах Actions
  как `ОШИБКА в поиске «...»`.
- **Пропущенные объявления.** Если сайт выложит пачку разом — подними
  `max_pages` до 3.

## Как добавить ещё один сайт

Новый модуль в [`sources/`](sources/) с двумя вещами: `NAME` и функция
`fetch(url, page)`, возвращающая объявления в общем формате (он описан
в [`sources/__init__.py`](sources/__init__.py)). Если детали приходится
догружать отдельным запросом — добавь `enrich(item)`, она вызывается только
для новых объявлений. Дальше — вписать модуль в `SOURCES` и добавить блок
в `config.yaml`.
